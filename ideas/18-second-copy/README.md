# Second Copy
> Pairs every number PartForge's flight doctrine, its GRADE_SY literal and its seven flight templates restate from its own tables with the row it repeats. At 0974a62, 125 copies agree, 18 have no row behind them (the doctrine's p6 zones, the SAE bolt grades), and 9 disagree: among them a bulkhead that names AS568-250, a W .139 ring, for a groove cut for W .103, and a template NOTE that differs from the copy the app ships. Replayed on the doctrine of 2026-09-18 it flags 15 of 16 UN clearances, the block PartForge's evaluation caught by hand.

**Kind:** linter
**For:** PartForge
**Run:** from the bank root, `node ideas/18-second-copy/second-copy.mjs` (reads the checkout at `/home/user/Partforge`; `--snapshots` reads this folder's snapshots instead; `--history` adds the two replays; `--all` lists every pairing, `--brief` one line each, `--unpaired` the numbers nothing claimed, `--json` an envelope in the shape of PartForge's headless CLI; `--doctrine FILE`, `--template FILE`, `--grade-sy FILE` lint your own text; `--help`; exit 0 nothing disagrees, 1 a DISAGREES or COPY-DRIFT, 2 refused, 3 usage). `example.txt` is saved output of three runs (the default, the history replays, the copy check as JSON). `ideas/18-second-copy/index.html` shows every pairing and lints pasted text (classic scripts, works from `file://`, no network). ## What it is

PartForge's flight grade tells a model how to design rocket parts in one long prompt, the *doctrine* (`flightSystemPrompt()` in `index.html`), and ships reference tables beside it (`data/tables/*.json`: ISO and UN fasteners, ISO 286 fits, AS568 O-rings with Parker glands, NASA design factors, motors, airframes). Wherever the doctrine, the bolt-strength table in the code (`GRADE_SY`) or a shipped template types a number the tables also carry, there are two copies of it, and only one of them is checked by anything.

Second Copy finds those second copies and compares them:

- **It pairs.** Each number is paired with the table key written next to it (`M6`, `#8-32`, `1/4-20`, `H7`, `g6`, a cross-section `W .103`, `AS568-250`, a bolt grade, `protoflight`), and with the column the sentence names (ISO 273 medium, B18.2.8 close, tap drill, Chart 4-3 liquids width…). The matched text is printed with every verdict, so a reader can check the pairing.
- **It judges** each pairing as **AGREES**, **DISAGREES** (both values printed; the only verdict that fails a run besides copy drift), **UNBACKED** (a key it recognises, but no row carries it; not called wrong), **NON-CLASS** (a clearance hole for a thread, no class named, that is none of the table's classes; the reason the line gives is quoted), **MAPPED** (no row, but the code reads it as one by an assumption the tool states) or **QUOTED** (a number inside a sentence that reports a past error).
- **It compares copies.** Each `tests/templates/*.scad` file line by line against the copy of it that `index.html` actually ships (**COPY-DRIFT**).
- **It replays history.** The doctrine's fastener, fit and O-ring bullets at `ad4d587` and `3bffbe0` against today's tables, to show the drift PartForge has already had once, found mechanically.
- **It counts what it did not pair.** Every number it did not claim is listed by `--unpaired`, so its coverage is visible rather than implied.

## Why I made it

**The open item.** PartForge's own test for this is `tests/flight-db.test.mjs:57–69`, "the doctrine does not contradict the tables". Its comment states the rule: *"Nothing in the doctrine may restate a fastener number the tables carry."* What it enforces is one regex of four strings at `:66` (`#4 3.26|#6 3.80|1/4 6.76|5/16 8.43`), the four the doctrine carried until 2026-09-18, plus two presence checks. `docs/roadmap-evaluation.md` records why: "What this evaluation already changed", bullet 3 (`:42–45`), and idea #44 (`:812`, "the doctrine still hand-types UN clearances shifted one class, contradicting the data the app serves"); build-first item 2 (`:246`) asks for a data-integrity sweep. The rule is general; the guard is four strings. Meanwhile the doctrine still restates 23 metric clearances and tap drills (`index.html:1493`), 15 ISO 286 zones (`:1494`), 20 Parker gland bands (`:1495`) and more, and `GRADE_SY` (`:5804`) restates the ISO 898-1 yields; no test checks any of them against its table.

**What I checked before building.** The four regexes, the doctrine slice (`tests/run.mjs:24–31`), `GRADE_SY` at `index.html:5804` with grade 2 present and unknown grades refused (the evaluation's `:4929` is stale, as idea 02 found), the p6 values at `:1494` with no `p` letter in `fits.json`, the metric and Parker numbers against their tables, and the two template hole sizes the proposal named. All held. Building it turned up the rest of the table above.

**Alternatives weighed.**

- *Delete the restated numbers from the doctrine and point at the tables*, as the evaluation did for the UN block. That is PartForge's decision, not a deposit's, and the doctrine's numbers are there for a reason: the reference hint only carries rows for the request at hand, while the doctrine is always in context. A linter keeps both and checks the second copy.
- *Generate the doctrine's numbers from the tables* (a `${…}` template the way `flightMaterialsTable()` already is). Better in the end, and it is in *Where it would land*; but it only covers sentences someone rewrites, and it says nothing about templates, `GRADE_SY` or the NOTE lines a model writes.
- *A generic number-near-a-key scanner* (the proposal's "tokenise into key/number/unit triples within a short window"). Tried on paper against the real text, it mis-pairs exactly where it matters: "M6 class 8.8 bolts, clearance 6.40" pairs M6 with 8.8; "4 x 6.60 holes = 1/4 in all-thread clearance (6.35 + 0.25)" pairs the hole with 6.35, its reason; the gland widths are positional ("liquids a / b / c / d" means the four cross-sections of the previous clause). So the resolvers here are explicit sentence shapes, each with its example in the code, and every number they do not claim is counted.

This won because it is the smallest thing that turns the rule in the comment at `:61` into a check, it refuses to call a missing row wrong, and it found real defects on its first run.

## How it works

**Inputs.** From a checkout: `index.html` (the doctrine is ``html.slice(indexOf("return `", indexOf("function flightSystemPrompt(){")) + 8, indexOf("`;", …))``, the slice `tests/run.mjs:27–30` takes; `GRADE_SY` with the comment block above it; the seven `code:` template literals pushed onto `TEMPLATES_FLIGHT`, unescaped), `tests/templates/*.scad`, and eight tables. Each table goes through one excerpt function in `second-copy.js` (`EXCERPT`), used by `build-data.mjs` to write the snapshots and by the CLI on the live JSON, so `--repo` and `--snapshots` read the same shapes; a test checks they give identical findings.

**The declared tolerance.** A printed literal *agrees* when it equals the table value rounded to the literal's own precision: |literal − table| ≤ ½ unit in its last printed digit (+10⁻⁹). So `6.75` agrees with 17/64 in = 6.746875 mm, `6.76` does not, `3.17` and `3.18` both agree with .125 in = 3.175 mm, and µm integers are held to ±0.5 µm. Where a table keeps inches as the authority and mm as a rounded copy (fasteners_un, AS568, Parker), the comparison uses in × 25.4 exactly. UN clearances agree with either the named drill or ASME B18.2.8's printed nominal, both of which the table carries (`clearance_*_in`, `clearance_*_nom_in`). The rule's limit is honest and tested: a literal printed as `7` cannot be told from 6.6.

**Verdict details.** A fit zone is the µm interval about the nominal, H holes 0…+IT, h shafts 0…−IT, d e f g shafts es−IT…es, k and n shafts ei…ei+IT with k's deviation zero outside grades 4–7; a test runs PartForge's own `dbFit()` (cut verbatim from `index.html:4997–5012`) beside it over every step, letter and grade. A letter the table does not carry is UNBACKED, and its width is checked against the IT grade: the doctrine's three p6 zones are each exactly IT6 wide (13, 19, 25 µm), so only the deviations +22, +32, +43 µm are without a row. A declared zone (`d_mm ± tol_mm`) agrees with a named fit only when both limits agree at the declaration's precision. A NON-CLASS hole lists every class of the table; its stated reason is the parenthesis right after the number or after "clearance", or the parameter comment after "clearance:". A DISAGREES or NON-CLASS fastener value also says which other row and column of the same system it *does* equal at its printed precision: that is how the replay of 2026-09-18 reproduces the evaluation's diagnosis.

**History.** `build-data.mjs` reads `git show ad4d587:index.html` and `git show 3bffbe0:index.html`, slices the doctrine the same way, and keeps its three table-number bullets (`- Use standard sizes`, `- Fits`, `- O-rings`). `ad4d587` is the commit before the UN numbers were deleted; `fasteners_un.json` is byte-identical from `fae75b8`, where it first shipped, to `0974a62` (same sha256), so for the UN block this replay is what a check would have said that day. `3bffbe0` is the commit before the tables existed; replaying it shows the O-ring line the tables' own reconciliation later corrected.

**The page** runs the same module on the same UMD snapshot files the CLI's `--snapshots` mode `require()`s: totals, the nine failing pairings with both values, every pairing by source with filters, and a box that lints pasted text (refusing an empty paste, and saying what it needs when nothing pairs).

## Honest assessment

- **[Certain] Every verdict is the comparison the rules above describe, on the table values PartForge ships.** The tables are read through one excerpt function, the fit arithmetic matches `dbFit()` itself over every case, and the verdicts that matter are each pinned to a value outside this code.
- **[Certain] AS568-250 is a W .139 ring.** `orings_as568.json` row -250: `id_in` 4.984, `cs_in` 0.139, series 2xx; the W .103 row nearest that ID is -159 (`id_in` 4.987). The bulkhead's groove (3.10 wide, 1.96 deep, inside Chart 4-3's W .103 bands, both checked here) is cut for W .103. A -250 ring in it would not fit: its section is π/4 × 3.531² = 9.79 mm² against a 3.10 × 1.96 = 6.08 mm² groove. Which dash was meant, and whether the groove ID moves with it, is the maintainer's call; the tool proposes nothing.
- **[Certain] The nose cone's pocket has two tolerances.** Its MAKE and NOTE lines say "ream 20.00 H7" (20.000–20.021 by `fits.json`); its FLIGHT bore, the one the CMM measures, declares ±0.05. A 19.96 mm pocket passes the check and fails the callout. The doctrine itself says "Name the fit in a NOTE; put its numbers in tol_mm" (`index.html:1494`), which the doctrine's own FLIGHT example (`:1440`, g6 cited, ±0.05 declared) does not do either.
- **[Likely] "Four vendors share ID 152.4" is a fair DISAGREES, not a quibble.** Three vendors' 6 in tubes are 152.4; PML's are 152.578, which PartForge's own test records (`tests/flight-db.test.mjs:34`). The doctrine's next words are "design to the dimension the vendors SHARE", and a ring designed to 152.4 − 0.10 has 0.28 mm in a PML tube instead of 0.10. Reading "four" as "the four vendors the hint lists" is my interpretation of the sentence.
- **[Certain] UNBACKED is not wrong.** p6 at +35/+22 µm may well be ISO 286's value; the tool cannot know, because `fits.json` withholds the interference letters on purpose (its notes, LIMITS (2): "a press fit taken from a half-remembered table is how a coupler cracks"), and PartForge's reference hint refuses p6 (`tests/flight-db.test.mjs:137` asserts the refusal). The doctrine gives the model the numbers the hint refuses to give. Likewise the SAE J429 grades (393 / 634 / 896 MPa) and "18-8" have no table at all; nothing here retypes them from memory or corrects them.
- **[Likely] a4-80 → A2-80 is an assumption, stated as MAPPED.** The table carries A2 classes only; that ISO 3506-1 gives A4 the same class-80 properties is from memory and not verified against the standard here.
- **[Certain] The resolvers are fitted to the sentence shapes PartForge's doctrine and seven templates use.** Model-written NOTE lines will vary; a shape not listed is not paired. That is why every unclaimed number is counted: 119 of the doctrine's 272 numbers are claimed, and most of the rest are not table numbers (process rules, MODE numbering, example JSON). The identifier mask that decides what counts as "a number" is heuristic; only the inventory depends on it.
- **[Certain] The history replays compare old text with today's tables.** For the UN block at `ad4d587` that is exact (the table has not changed). For `3bffbe0` the tables did not exist yet; its six flagged bands are exactly the six the table's own reconciliation names, which is the evidence that the comparison is the right one.
- **[Speculative] Whether a linter is the right end state.** I think generating the doctrine's numbers from the tables is better for the doctrine, and a linter is still needed for templates and NOTE lines; that is a design call for PartForge.
- **Rough.** Pairing within prose is per line and per clause (split at `;`), so a key and its number on different lines are not paired. QUOTED needs "said" or "used to" before the number in its clause. The copy check is line-based (LCS), so a moved line shows as one removed and one added. The page cannot read `.scad` files from `file://`, so its snapshots are UMD-wrapped strings (hashed against the source files by the tests). PartForge's vocabulary (`certain / likely / recall`) is printed on table values as the tables carry it; the bank's `[Certain]/[Likely]/[Speculative]` is used only in this README.
- **Fidelity.** An idea-bank prototype. It has not been through PartForge's data-provenance pipeline (`tools/db/`, `tests/flight-db*.test.mjs`), its geometry gate (no template was compiled here) or a skeptic review, and none of its findings has been confirmed by a PartForge maintainer.
