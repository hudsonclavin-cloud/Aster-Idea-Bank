# Blue Cells
> Reads the Skyhook financial workbook's 14 × 3 input ladder straight out of the .xlsx with nothing but `zipfile` and `xml.etree`, writes it as one JSON artefact carrying the file's sha256 and the md5 that `finance/decision_grid.json` records, and reports what the committed file stores: 146 formula cells and zero computed results. The "post-fix workbook results" in `docs/DECISION_LOG.md` item 6 were never read from this file; they follow from its formulas, which this deposit's tests evaluate on the extracted inputs and reproduce (121.83× / 609 t / $8,741M / Y9 / Y7).

**Kind:** tool
**For:** Skyhook
**Run:** from the bank root, `python3 ideas/08-blue-cells/ladder_export.py` (reads the snapshot workbook, prints the one-screen report; give it any `.xlsx` path to read another copy; `--out ladder.json`, `--js page-data.js`, `--format json`, `--provenance <sidecar>`, `--rows-map <json>`; exit 1 when the sheet does not hold the ladder where the row map says, exit 2 for a file it cannot read). The saved run against the checkout is `example.txt`. `index.html` shows the same run and lets you drop your own copy of the workbook on it (plain classic scripts, works from `file://`, nothing is uploaded). Tests: `python3 -m unittest discover -s ideas/08-blue-cells -p 'test_*.py'` (42 tests, about 1 s), `node --test ideas/08-blue-cells/bluecells.test.mjs` (18 tests, under 1 s) and `node ideas/08-blue-cells/ui-check.mjs` (44 checks in headless Chromium through the globally installed Playwright; `check.mjs` runs it for `tools/check.mjs`). Rebuild the derived data with `python3 ideas/08-blue-cells/build_data.py /home/user/skyhook`.
**Made by:** Quire

## What it is

`tools/financial/skyhook_financial_model.xlsx` is the Skyhook program's financial workbook. Its own README sheet says how to read it: *BLUE = hardcoded inputs · BLACK = formulas · GREEN = cross-sheet links · YELLOW fill = key assumption needing attention*. The blue cells are the conservatism ladder (fourteen assumptions in three columns, Conservative / Baseline / Optimistic), the shared Rev A design point and two physical constants. Everything else in the file is a formula over them.

`finance/skyhook_finance.py` is "reconciled, by construction, to the corrected workbook" by reading those blue cells with openpyxl. Nothing else in the repository, and nothing in the browser, can read them without that library. `ladder_export.py` reads them with the Python standard library only: an `.xlsx` is a zip of XML parts, so the tool opens `xl/workbook.xml`, the workbook relationships, `xl/styles.xml` (fonts and fills, so a cell's colour can be read), `xl/sharedStrings.xml` when a file has one, `docProps` and every worksheet part, and records for every cell its reference, type, formula, cached value and colour. It then:

1. **Extracts the ladder** keyed by the names `skyhook_finance.py` uses (`_LADDER_ROWS`, `SCENARIOS` and the column letters, read out of that module by `build_data.py` with the `ast` module and snapshotted as `snapshots/ladder_rows.json`, never retyped), after checking that the label in column A of each mapped row says what the key means. A sheet whose rows have moved is refused with the row, the label found and the label expected; `fixtures/shuffled_assumptions.xlsx` (rows 5 and 10 swapped) shows the refusal in `example.txt`.
2. **Writes `ladder.json`**: the 42 ladder cells with their raw text, their cell references, the sheet's own "Source / note" column, the shared design point (B19:B28) and constants (B32:B33), the workbook's sha256 and md5, who wrote it and when, the `calcPr` flags, and a per-sheet census. No timestamp of its own, so two runs give the same bytes.
3. **Takes a census of what the file stores**: per sheet, how many cells hold a formula and how many of those also hold a cached result; how many are literal numbers; how many carry the blue input font, the green cross-sheet font or the yellow fill. The answer for the committed file, at every version in reachable history: **146 formula cells, 0 cached results**. The `<v>` element under every formula is empty. The file was written by openpyxl 3.1.5, which never calculates, and its `calcPr fullCalcOnLoad="1"` tells a spreadsheet program to recompute everything on open. So the workbook carries inputs and formulas, not results, and any number quoted as a "workbook result" was computed somewhere else.

The report at `34935cb` (`example.txt`):

| README | 6 | 0 | 0 | 0 | 6 | 0 | 0 | 0 |
| Assumptions | 106 | 0 | 0 | 54 | 52 | 54 | 0 | 3 |

The 63rd blue cell is the Cash Flow sheet's scenario selector `B2` ("Conservative", a string); the other 62 are numbers. The 19 literal numbers on the Cash Flow sheet are the zeros for the pre-operations years, in the default font, not blue. The only computed output inside the file is `xl/media/image1.png` (53,976 bytes, md5 `11384969e42362346381174c57ddc7ae`), byte-identical to `tools/financial/cashflow_chart.png`: a matplotlib picture of the Python model's cash flow, placed on the Cash Flow sheet in commit `5719c0e` under the note "Static snapshot (Conservative scenario) — see finance/skyhook_finance.py for the live scenario-driven model."

For contrast, `fixtures/recalculated_by_libreoffice.xlsx` is the same workbook after headless LibreOffice opened and re-saved it (`build_data.py` makes it when `soffice` is on the path): 146 formula cells, **146 cached results**, 158 shared strings, writer `LibreOffice/24.2.7.2`, the same 42 blue inputs. Its stored results are an independent engine's evaluation of the sheet's formulas: Design Calcs `B11` × 2 = 121.83, `B12` = 609.13 t, Cash Flow `B4` = 8,741.09 and `B16` = "beyond Y15", the figures DECISION_LOG item 6 quotes. It also shows the one formula block in the file that is wrong (finding 7 below), which no one could see in a file that stores no results.

`bluecells.js` is the same reader in JavaScript (a central-directory zip walker with CRC-32 checks, a regex XML cell parser, MD5), so `index.html` can run it on a workbook you drop on the page, through the browser's own `DecompressionStream`, and compare the result cell by cell with the snapshot. The Node tests hold the two implementations to the same JSON, the same text report and the same refusal message.

## Why I made it

The open items this serves, with where they are written down:

- `finance/skyhook_finance.py:10-12` — "Ladder assumptions are READ from the workbook 'Assumptions' sheet with openpyxl in read-only mode, so this model starts reconciled"; `:107-110` — the import is local "so the physics-only CI environment can still import this module's pure functions". The ladder is the one place the finance model's inputs live, and only an openpyxl process can see them.
- `docs/DECISION_LOG.md:47` — "Post-fix workbook results: Conservative 121.83× / 609 t / $8,741M / payback ~Y17; …" and `tests/test_finance.py:4-8` — "Reconciliation targets are the post-correction workbook figures". A committed file that stores no results cannot be the source of those figures. Nothing in the repository looked: `load_ladder_from_workbook` opens the file with `data_only=False` (`skyhook_finance.py:112`), which reads formulas and never asks for cached values.
- `finance/decision_grid.json` carries a `workbook_md5` (`5ccdee4d43e91f8dd98884678c8e99bb`), computed by `export_grid.provenance_md5` on the raw bytes because the workbook is a zip (`finance/export_grid.py:86-93`). Closing that loop from outside openpyxl, in a browser or a CI job without it, needs a reader that hashes what it read.
- The bank's `BRIEFING.md` §4: each project "has been bitten by a number quoted from memory"; the Skyhook calculator simulators hardcode this ladder's `launch: 2500 / 1500 / 800` (noted in idea 04's README), and five other candidate ideas in this bank's proposal round needed the ladder as JSON.

What already exists, and why it is not this: `load_ladder_from_workbook` returns dataclasses to Python callers that have openpyxl, and nothing to anyone else; `export_grid.py` hashes the file but does not read it; `test_finance.py` checks the derate ladder against `rev_a.json` but only after openpyxl has read it. None of them can say what the file stores.

Alternatives I weighed. (a) Commit a hand-written `ladder.json` beside the workbook: a second copy of fourteen numbers with no way to know when it drifts. (b) Have `skyhook_finance.py` write `ladder.json` as a side effect of its openpyxl read: solves the browser's problem, keeps the dependency, and still never looks at cached values. (c) A general xlsx-to-JSON converter: more code, and it would return the wrong row's number under the right name the first time the sheet is re-laid-out. (d) This: a reader for *this* workbook's shape, keyed by the finance module's own row map, that refuses when the labels do not match, hashes what it read, and counts what the file stores. The census was the part the proposal's judges valued most, and it is the part no library path produces.

## How it works

**The zip and the XML** [Certain]. Python: `zipfile` for the archive, `xml.etree.ElementTree` for every part, namespaces stripped by local tag name. JavaScript: the zip's end-of-central-directory record is found by scanning back from the end (an archive comment may follow it), the central directory gives each member's method, CRC-32, sizes and local-header offset, and the data start is read from the local header (its own name and extra lengths, which can differ from the central directory's). Stored (method 0) and deflated (method 8) members are read; deflate is injected by the host (`zlib.inflateRawSync` in Node, `DecompressionStream('deflate-raw')` in the browser); every inflated member must match its declared size and CRC-32. ZIP64 is refused. The XML cell parser is a regular expression over `<sheetData>` that handles `<c …/>`, `<f>` with or without a body, `<v/>`, `<v>…</v>`, `<is><t>` runs and the five named plus numeric entities; the Python side gets the same result from ElementTree, which is the point of having two.

**Cells** [Certain]. Each `<c>` becomes `{ref, col, row, t, s, formula, cached, kind, value, raw, font_rgb, fill_rgb}`. A cell with an `<f>` child is a formula whatever its `t`; its cached value is the text of a non-empty `<v>`, else `None`. Otherwise `t="s"` indexes `sharedStrings.xml` (an index the part does not have is a `WorkbookError`), `t="inlineStr"` concatenates the `<t>` runs, `t="str"`, `t="b"` and `t="e"` are string, bool and error, and anything else with a `<v>` is a number (`float`; the raw text is kept, so the report prints `1` and `0.465` as the sheet does). A numeric cell with no `<v>` (`<c r="E15" t="n"/>`) is *empty*; `<v>0</v>` is the number zero. Colours come from `styles.xml`: the cell's `s` indexes `cellXfs`, whose `fontId` and `fillId` index `fonts` and `fills`; the RGB part of the ARGB `rgb` attribute is compared with `0000FF` (blue), `008000` (green) and a solid fill of `FFFF00` (yellow), the three colours the README sheet's legend names.

**The ladder** [Certain for the read; the drift guard is this tool's choice]. `snapshots/ladder_rows.json` holds, from `finance/skyhook_finance.py` at `34935cb`: `_LADDER_ROWS` (lines 56–71: fourteen keys → rows 3–16), `SCENARIOS` (line 52), the `cols` map `{Conservative: B, Baseline: C, Optimistic: D}` (line 114) and the sheet name (line 113). The reader finds the header row (column A reads `Parameter`) and requires each scenario column's header to equal its name. For each key it requires the column-A label of the mapped row to contain a fragment from `LABEL_GUARD` (`construction_launch_per_kg` → "launch price during construction", `customer_price_per_kg` → "price to customer", and so on; the same table in both implementations, which a test checks), and each of the three cells to be a literal number, not a formula, not empty. Any miss is collected and the whole extraction is refused with every miss listed and what would help. The design point and constants are read as the rows with a string in A and a number in B under the `SHARED DESIGN POINT` and `PHYSICAL CONSTANTS` headers, keyed by a slug of the label up to its first " — " or ";" (`CoM altitude (km)` → `com_altitude_km`).

**Census and checks** [Certain]. Per sheet: cells, formula cells, formula cells with a cached value, literal numbers, strings, empties, blue cells, blue cells holding a formula (should be none), green cells, green cells that are not cross-sheet formulas (should be none), yellow-filled cells. Six checks are reported with the ladder: rows found where the map says with matching labels; all 42 ladder cells literal; all 42 in the blue input font; no blue cell holds a formula; every green cell is a formula referencing another sheet; a design point was found. Only the first two can refuse; the colour checks are reported, because a restyled sheet still carries the right numbers.

**Hashes** [Certain]. sha256 and md5 of the file's bytes, binary, no line-ending normalisation: the same choice `export_grid.provenance_md5` makes for suffixes it does not list as text (`finance/export_grid.py:86-93`), which is why the md5 here equals `decision_grid.json`'s `workbook_md5`. The JavaScript MD5 is RFC 1321 written out (sine-table constants, 64 rounds) and is tested against the RFC's vectors and Node's `crypto` at block boundaries; its sha256 comes from WebCrypto when the page has it.

**What every number on the page traces to.** The page computes nothing; `page-data.js` is `ladder.json` wrapped as a classic script, written by `--js` in the same run as `example.txt` (a test checks the two JSONs are equal). The header's commit, date and the file's last change come from `snapshots/skyhook_financial_model.xlsx.provenance.json`, embedded with `--provenance`. The drop zone runs `bluecells.js` on the dropped bytes and compares with the embedded run; a refused file shows the refusal and no ladder.

**Data.** `snapshots/skyhook_financial_model.xlsx` is a whole copy made with the bank's `snapshot.mjs` (sidecar: `34935cb`, blob `3fa20f9`, read bytes equal the committed blob). `snapshots/rev_a.json` is a `--pick` excerpt (`materials`, `mass_ratio`, the reference tip speed, the lower-tip speed, `orbital`, `geometry`, `_meta`) and `snapshots/decision_grid.json` a `--pick` of the grid's five provenance fields; both for the tests only. `snapshots/ladder_rows.json` and `snapshots/DECISION_LOG.md` (lines 45–57, item 6, every other line left empty so `file:line` still matches) are derived by `build_data.py` and carry `--sidecar-only` provenance. `snapshots/ladder.json` is this tool's own output with a sidecar naming the workbook it was derived from. `fixtures/shuffled_assumptions.xlsx` is the snapshot with Assumptions rows 5 and 10 swapped and the chart parts removed (14,601 bytes), made by `build_data.py`; it is a fixture, not a snapshot, and has no sidecar. `fixtures/recalculated_by_libreoffice.xlsx` (69,458 bytes) is the snapshot after `soffice --headless --convert-to xlsx`, also made by `build_data.py`; LibreOffice stamps the file, so its bytes are not reproducible while its values are, and the tests check values. openpyxl 3.1.5 happens to be installed in this sandbox and one test uses it; the tool never does.

## Honest assessment

- [Certain] The counts are what the bytes say. Every formula cell in `tools/financial/skyhook_financial_model.xlsx` at `34935cb` has an empty `<v/>`; the same is true of the four earlier versions of the file in reachable history (`30419ef`, `9bdb224`, `138a9bd`, `8cff680`), each with 146 formula cells. The file names its writer (openpyxl 3.1.5) and asks the opener to recalculate (`fullCalcOnLoad="1"`). I ran the tool on each old version in scratch to check this; those runs are not shipped.
- [Certain] The workbook is not wrong. It carries the right inputs (the derate ladder, tip speed, σ, ρ, SF all equal `rev_a.json`) and formulas that, evaluated, give exactly the figures DECISION_LOG item 6 and `test_finance.py` quote. What is loose is the provenance wording: "workbook results" and "workbook figures" for numbers that a spreadsheet program produced on open and nobody saved, or that `finance/skyhook_finance.py` produced. The tests here are the first thing in either repository that evaluates the sheet's own formula chain on the sheet's own inputs and checks the published figures against it; the agreement is to the dollar after rounding.
- [Likely] Which of the two produced the DECISION_LOG figures I cannot tell from the repository. The log says "post-fix workbook results", the Python model's docstring says it "reproduces the workbook within 5%", and the two agree because they are the same arithmetic. The README names both.
- [Certain] The extraction and the drift guard do what this README says; the sabotage table shows which tests notice which break. Two breaks abort the Python suite in setup rather than failing tests: that is still loud, but a reviewer should know the count is "0 run", not "38 fail".
- [Likely] The reader is written for this workbook's shape, not for spreadsheets in general: one ladder block with a `Parameter` header row, labels in A, a note in E, section headers in capitals. It handles shared strings, stored members, archive comments, string formula results and rich-text runs because a copy saved by a spreadsheet program has them; the LibreOffice-saved copy exercises shared strings, cached numbers and a cached string result on a real file, the rest only on synthetic files. I had no Excel-saved copy. It does not handle ZIP64, encrypted workbooks, `.xlsb`, or formulas shared by reference (`<f t="shared" si="0"/>` with an empty body: counted as a formula, body empty).
- [Certain] The label guard is a table I wrote by reading the sheet once. It makes a re-laid-out sheet fail loudly; it would not catch a sheet whose labels keep their words and change their meaning. The row map and the guard have to move together, and the refusal says so.
- [Certain] The page shows one saved run and the result of a reader on a dropped file. It computes no economics, states no payback, and the blue on the page is this page's colour for "the workbook styles this cell as an input", not the workbook's exact `#0000FF` (which is unreadable in dark mode). In headless Chromium the clipboard is unavailable, so the Copy buttons fall back to showing the text; the check accepts either.
