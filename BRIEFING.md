## 1. Aster (asteroid-mining-planner)

**What it is [Certain].** A browser asteroid-mission planner that also answers mission-analysis questions over MCP, where every number carries its source, its confidence class and the commit it was computed from. Live at `https://hudsonclavin-cloud.github.io/asteroid-mining-planner/` with routes `/v2/solar-system/` (3D solar system plus a 41,906-body near-Earth-asteroid catalog), `/v2/porkchop/` (C3, ΔV, declination of the launch asymptote, delivered mass), `/v2/compare/` (Slice 17 target compare) and `/v2/about/` (validation evidence). The MCP package `aster-mission-mcp@0.1.0` ships seven tools (`search_bodies`, `get_body`, `porkchop_scan`, `explain_cell`, `dla_feasibility`, `estimate_mission_cost`, `get_validation_report`) and compiles the same `src/v2` core the browser runs, so there is one math implementation, not two.

**The thesis [Certain, quoted from `ASTER_PRODUCT_VISION.md`].** Which specific asteroids are actually accessible is computable; Aster makes that fraction computable in a browser with honest orbital data, real mission-cost calculation, and later composition and economics. The house line (`strategy/ASTER_FAMILY_MASTER_PLAN.md`): *if the system cannot explain why it ranked, screened or recommended something, it does not present the output as strong.* A kernel that cannot refuse does not ship.

**Stack [Certain].** TypeScript, Preact, Three.js **r128** (no `texture.colorSpace`, no `CapsuleGeometry`, no CDN OrbitControls), Vite. Tests: `node --test tests/*.test.mjs`. `src/v2/core/**` is a protected surface (hook-enforced; edits need a signed dispatch). `AGENTS.md` is the operating system for agents; `INVARIANTS.md` the facts not to violate; `STATUS.md` the current state; `src/v2/SLICE_*_FOUNDING.md` the per-slice design records (additive-only).

**Where the truth lives [Certain].**
- Lambert solver: `src/v2/core/lambert/izzo.ts` (clean-room Izzo 2014, poliastro is the oracle, never ported); multi-rev in `lambert-multi-rev.ts`; DLA in `dla.ts` (`asin(vz/|v|)` on the departure v∞ **with no ecliptic→equatorial rotation**, because the frame was measured to be ICRF, DEC-12-2/INV-021); launch-site bands in `feasibility.ts` (Cape Canaveral iMin 28.5°, ceiling 57°; Vandenberg iMin 70°, ceiling 90°; GREEN/AMBER/RED by |DLA| against the corridor, never against latitude).

## 2. PartForge

**What it is [Certain].** Describe a part, or show a photo, and get a printable 3D model: a model (Claude by default; OpenAI-compatible endpoints, Gemini and a key-free Replay mode are supported) asks clarifying questions, writes parametric OpenSCAD tuned for FDM, `openscad-wasm` compiles it to a mesh in a Web Worker, three.js previews it, and the page hands you STL/3MF plus a moving-assembly preview for mechanisms. **Flight grade** turns the same tool on machined and engineering parts for a university rocket club: a `FLIGHT` declaration in the file, a mesh CMM that measures the finished geometry against the declaration, recomputed engineering checks, mass/CG/inertia at the material's density, a manufacturing sheet, an interface control drawing for tier B/C parts and a JSON measurement report. Live at `https://hudsonclavin-cloud.github.io/Partforge/`. One HTML file (`index.html`, 1.2 MB), no backend, no build step; `server.mjs` is an optional local key-holding proxy; `worker.js` a Cloudflare Worker relay; `engine-study.html` a separate educational page.

**The gate [Certain].** A generated part opens with a `SPEC` block (parts, sizes, joints, proportion rules, layout relations, shape profiles) travelling as comments. The program renders every declared part alone, every joint as an `intersection()` (and measures the shared volume's thickness, since touching faces intersect in a zero-thickness sheet), every rule and relation, and whether `main()` actually contains the declared parts. A failure is fed back quoting the model's own promise; retries are 2 + one per declared part, capped at 6, keeping the best candidate; a retry may add to its declaration but never fall below it. Whole-mesh checks (floating pieces, on-plate, bed fit, watertight, volume) run underneath. The intent judge is advisory and never rejects.

**Headless [Certain].** `headless/cli.mjs` runs the app's own checks with no page: `check part.scad` (JSON envelope; exit 0 pass / 1 fail / 2 refused / 3 usage), `render --stl`, `lookup "<hardware phrase>"`, `templates`, `doctrine [flight|hobby]`, `dxf`, `credits`, `provider-check`, `design`. `headless/mcp.mjs` exposes the same as an MCP server. `core.gen.mjs` is **generated** from `index.html` by `build.mjs` (186 of the script's 429 statements copied out unedited), so headless and browser verdicts are the same code.

**Reference data [Certain] — `data/tables/*.json`, one shape:** `{table, license_note, columns, rows: [{key, confidence: certain|likely|recall, source, …}], notes, reconciliation}`. Tables and sizes (bytes ÷ 1000 at `0974a62`; an earlier draft of this briefing listed `du` block counts, corrected after idea 06's review traced a wrong figure to it): `airframes` 396 KB (from openrocket-database `.orc`, Apache-2.0; 161 of 291 rows are recall), `avionics` 62 KB, `design_factors_nasa` 18 KB (NASA-STD factors of safety and fastener rules, quoted with clause tags; public-domain US-government text), `drills` 284 KB, `fasteners_metric` 58 KB, `fasteners_un` 108 KB, `fits` 17 KB (ISO 286 IT grades and fundamental deviations **derived from the standard's formulas**, five disagreeing values withheld), `materials_thermal` 16 KB (ν, CTE, service_max_c for the 21 flight materials), `motors` 207 KB and `motor_perf` 742 KB (certified peak thrust and more; 29 recall rows), `npt` 42 KB, `orings_as568` 361 KB (AS568 dashes with Parker glands), `rails` 61 KB, `stock` 384 KB (6061 stock; 148 of 192 rows recall). Four selectors in the app turn rows into answers: `dbPickORing()`, `dbPickDrill()`, `dbPickStock()`, `dbBoreMm()`. `docs/data/PROVENANCE.md` has the attribution text per table. Test the tables through `tests/flight-db*.test.mjs`.

**What it already has (do not rebuild) [Certain].** Printer database (36 machines); the geometry gate and SPEC checks; flight CMM, tiers A/B/C, tolerance provenance counts (cited / user / tool-default); manufacturing sheet, ICD, measurement report; DXF **import** (units, layer, open-contour and self-intersection refusals, SPLINE reported not dropped); mesh tools (mirror, rotate, drop, scale, auto-orient); assembly explode and joint drivers; share links and QR; the bench (`?bench=1`); the Replay provider; the headless CLI/MCP; O-ring gland, drill, stock and bore selectors; `dbFitThermal()` (one-sided thermal fit term with a confidence label).

**What it has said it wants [Certain, from `docs/roadmap-evaluation.md`, the evaluation of 50 ideas by one scoper and independent skeptics].**
- *Build first:* (1) LICENSE + NOTICE — done since; (2) a data-integrity sweep: (a) `GRADE_SY` with no SAE grade-2 entry, so a grade-2 U-bolt got 640 MPa instead of ~393 — **fixed before the evaluation was committed**: its own preamble, "What this evaluation already changed" (`:27-34`), says to read the entries at `:246` and `:280` as history, and `GRADE_SY` at `index.html:5804` (at `0974a62`) carries `'2': 393` with an unknown grade refused; (b) the doctrine hand-types UN clearances shifted a fit class relative to the app's own `fasteners_un.json`; `recall` rows are stamped as cited provenance (161/291 airframe, 148/192 stock, 29/124 motor rows) and need a provenance state they cannot promote out of; two surface-finish lints from the shipped Parker gland data; (3) the loads plumbing foundation: a flight-envelope/load-case declaration block with provenance, a non-gating row state so a screening or refused row stops being an unfixable retry deadlock, cross-reference from a loads entry to CMM rows; (4) aero-heating stage 1 (stagnation/recovery temperature against `service_max_c`; 40 lines, no free parameters, three worked numbers reproduce against the repo's `isa()` and `ISA_GAMMA`) plus parachute opening shock with a `shock_ref` cross-row reference (the first cross-row dependency); (5) tolerance stack-up gated on worst case with RSS informational, using `fits.json`, `stock.json` asymmetric tolerances and the existing `dbFitThermal()`.

## 3. Skyhook (rotating momentum-exchange tether)

**What it is [Certain].** A rotating tether ("rotovator") with its centre of mass in a 610 km orbit, half-length 320 km, that catches payloads arriving on suborbital trajectories at its lower tip and releases them from its upper tip. Investment thesis: high-energy Δv substitution (GTO and beyond), **not** LEO upmass displacement. Reboost is electrodynamic (TSS-1R and TEPCE heritage). Phase 0 (paper study and materials qualification) is where the program stands.

## 4. Seams between the projects

- **Aster → Skyhook (K2).** Aster computes an Earth-arrival v∞ for a return leg; Skyhook's lower tip meets a payload at 290 km altitude moving 4.59 km/s ground-relative (or, for an inbound-from-deep-space payload, the question is the tether's catch envelope at the upper tip). The interface quantity is Earth-arrival v∞; tether constants come only from `params/rev_a.json`. Aster's master plan lists this as the **Aster Momentum** lens.
- **PartForge → Skyhook.** ST-001 needs rig hardware (capstan dowel grips with a tie-off, a scale bracket, a splicing fid for 1.75 mm line); TP-001 needs coupon fixtures. Those are parts PartForge exists to make, and the flight-grade doctrine (declared tolerances, measured geometry) is the right level for a test rig that must not break at the grip.
- **PartForge → Aster.** Both carry the same idea in different words: a number is only as good as its provenance (PartForge `tol_src: source / user / default`, confidence `certain / likely / recall`; Aster `measured / derived / assumed` with `sourceIds`). Skyhook uses `[Certain]/[Likely]/[Speculative]` and the manifest's `[Verified]/[Anchored]/[Planning]/[Demo]`. A shared vocabulary, or a translator between them, is itself an idea.
- **All three.** Each has been bitten by a number quoted from memory or a label that drifted from the data (Skyhook's 440× and 3.5-vs-2.5; Aster's literal "2026-2040" label and CRLF hash; PartForge's recall rows stamped as cited). Linting tools that catch canon drift, literal labels and provenance gaps are wanted everywhere and exist nowhere.
